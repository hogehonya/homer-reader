# 古典注釈プラットフォーム構想

**版**：構想メモ v0.1

**作成日**：2026年10月11日

**関連プロジェクト**：`homer-reader`、`requirements-engineering`、`design-rules`

**状態**：検討案。本文・注釈の編集方針、運営主体、ライセンス、課金方式は正式決定前。

## 1. 目的と背景

パブリックドメインの古典を、単に無料で表示するだけでなく、対訳・注釈・相互参照によって**理解しながら読み通せる形**で提供する。ホメロスから始め、マックス・ウェーバーなど思想・文学・歴史の著作にも広げる構想である。

古典の本文には長期にわたる価値がある一方、難解な概念、歴史的背景、翻訳上の問題が読書の障壁になる。本文の価値を作り直すのではなく、読書体験と信頼できる注釈体系によってアクセス可能にする。

現行の `homer-reader` は『イリアス』『オデュッセイア』48巻を収録し、日英対訳と注釈を表示する。注釈を個々の段落に埋め込むだけでなく、改訂・再利用・引用可能な独立した知識資産として扱う方向を検討する。

## 2. 基本構想

- **本文は安定した参照対象とする。** 対象箇所は作品・版・章・段落などの永続IDで特定する。本文の校訂や底本変更は、注釈の通常改訂と区別する。
- **注釈は独立した知識単位とする。** 語注、背景解説、概念記事を分け、異なる作品・箇所から再利用・相互参照できるようにする。
- **注釈の追加・訂正はGit型の提案・査読・マージで管理する。** 公開版への変更は履歴と判断理由を残す。
- **学説や解釈を一つの正解に無理に統合しない。** 事実訂正と、根拠のある異説の併記は別の編集操作とする。
- **一般読者にはGitを意識させない。** 読書画面では注を読むだけでよく、希望者が「注釈を提案する」から参加できる形を目指す。

これらは現時点での設計候補であり、各論の仕様は要求工学の手順で検証して確定する。

## 3. プラットフォームを誰が用意するか

「リポジトリ・レビュー機能を提供する主体」と「読書サービスを運営する主体」と「編集品質に責任を持つ主体」を分けて考える。

| 役割 | 初期段階の案 | 責任の範囲 |
| --- | --- | --- |
| Gitリポジトリ／PR基盤 | 既存のGitea、またはGitHub | 変更提案、差分、レビュー、履歴の提供 |
| 読書・公開プラットフォーム | ホニャプランが当面運営する案 | 表示UI、配信、利用者体験、運用 |
| 編集・品質管理 | ホニャプランを初期編集主体とし、協力者を募る案 | 注釈の採否、根拠確認、公開品質 |
| 投稿者・査読協力者 | 読者、研究者、翻訳者等 | 出典を示した提案、訂正、レビュー |
| 将来の共同運営主体 | 大学・研究会・図書館・出版社等との連携を検討 | 編集責任の分担、継続性、公共性 |

GitHubやGiteaがホスティングを担っても、注釈の学術的妥当性や編集方針に責任を持つわけではない。ここは独立した編集ガバナンスが必要になる。

**初期案**：既存の `homer-reader` とGitea／CI資産を活用し、PR運用を先に試す。GitHubは外部貢献者との接点として比較する。独自のGitホスティングや共同編集エンジンは、必要が明らかになるまで新規開発しない。Gitデータと公開用データは移行可能な形式で管理し、特定サービスへの依存を抑える。

## 4. 注釈の変更・査読フロー

1. 読者または編集者が、本文の対象箇所と注釈の追加・訂正内容を提示する。出典、理由、注釈種別を併記する。
2. 提案はIssueやPRとして記録する。一般読者向けの投稿フォームを用意する場合も、その後ろで既存のGit基盤につなぐ。
3. 自動検証でスキーマ、対象ID、リンク、出典情報、既存注釈との関係、ネタバレ属性などを確認する。AIは下書き・差分要約・整合性確認を支援するが、正しさを保証する査読者とは扱わない。
4. 編集者・必要に応じた専門家が内容をレビューする。事実誤認、出典不明、解釈の混同、著作権上の問題を確認する。
5. 採用・修正要求・不採用を記録する。根拠のある異説は削除せず、併記可能なモデルを用意する。
6. 承認済みの変更をマージし、CIで公開用注釈データを生成・検証して読書サイトに反映する。
7. 不適切な更新は履歴を保存したまま差し戻せるようにする。

## 5. データ構造の考え方

本文と注釈を同じJSONの中に恒久的に閉じ込めず、以下の概念を分離する。

| 概念 | 役割 |
| --- | --- |
| `Work` | 著作そのもの（例：『イリアス』） |
| `Edition` | 底本・校訂版・翻訳版。どのテキストを指すか明確にする |
| `Passage` | 章・節・段落など、版に結び付く本文の参照単位 |
| `Annotation` | 語注、歴史的背景、概念解説、解釈等の知識単位 |
| `Anchor` | 注釈が対象にする本文箇所・語句との関連 |
| `Reference` | 出典資料、引用箇所、関連する注釈・本文 |
| `Revision` | 提案者、査読、採否、変更理由、版履歴 |

同一概念を複数作品から参照できるようにする。一方で、版によって段落分割や表現が異なることを前提に、単なる文字列一致だけで注釈を結び付けない。

## 6. 公共的な知識基盤と商業サービスの分離

**検討案**：注釈の共同編集基盤はオープンに運営し、その成果を使いやすく構成・校閲・配信する読書サービスや編集版を有料提供する。

無料側の候補は、権利処理済み本文、公開注釈、出典・改訂履歴、訂正提案の入口。有料側の候補は、磨かれた読書UI、体系的な編集・校閲版、便利な参照機能、品質管理された音声など。ただし**無料／有料の境界と課金方式は未決定**とする。

注釈の再利用を認める場合は、投稿者の権利、クレジット、二次利用、商用利用を投稿前に明示する。本文、既存翻訳、生成音声の権利関係は別に確認する。オープン公開するからといって、投稿内容を無条件に商用利用できるわけではない。

## 7. 編集ガバナンスの論点

- **責任**：最終マージ権限と編集責任を誰が持つか。審査の専門性が足りない場合はどう扱うか。
- **品質表示**：AI草稿、出典照合済み、専門家校閲済み等を混同せず、実際に確認した範囲を示す。
- **異説**：事実訂正と学術的な解釈の対立を区別し、複数説の根拠と立場を示す。
- **権利**：注釈の投稿規約、採用ライセンス、引用・転載の範囲、商用利用への同意を定める。
- **貢献者**：執筆・査読のクレジット、匿名性、訂正申立て、利益相反の扱いを定める。
- **継続性**：運営主体の変更やサービス停止時に、公開データと履歴をどう引き継ぐか。

## 8. 段階的な実証計画（提案）

**段階0：設計と注釈資産の棚卸し**

`homer-reader` の既存注釈1,375件を対象に、独立ID・出典・対応箇所・査読状態の不足を確認する。`requirements-engineering` と `design-rules` で要件と読書体験を監査する。

**段階1：Gitによる注釈編集の実証**

少数の注釈を独立ファイルに切り出し、PRで追加・修正・査読・マージし、既存リーダーへ取り込む。読書画面や全文データは極力変更しない。

**段階2：読者参加の入口**

本文から対象段落付きで訂正提案できる導線を設ける。Gitの知識がない読者にも提案可能かを検証する。

**段階3：作品横断と事業化検証**

ウェーバーなどを追加し、概念注釈の再利用と複数解釈の扱いを検証する。読者の利用状況や、有料編集版への支払意思を確認する。

初期段階では独自のGitサービス、独自のPRレビューUI、全面的な共同編集CMS、課金システムを新規開発しない。

## 9. 検証すべき成果

- 注釈の提案からマージ・公開まで、出典と変更履歴を追跡できる。
- 不適切な注釈を却下・修正・差し戻しできる。
- 本文や既存の注釈を意図せず変更せずに、独立した注釈を追加・改訂できる。
- 読者が難しい箇所から注釈へ移動し、理解したら本文へ戻れる。
- 同じ概念記事を複数箇所から参照できる。
- 投稿者・編集者・公開主体の責任とライセンスが明確である。

これらは**将来の受入条件の候補**であり、現時点で検証済みの事実ではない。

## 10. 次に決めるべきこと

1. 注釈データの正本を `homer-reader` 内に置くか、作品横断の別リポジトリにするか。
2. PRの運用基盤を既存Gitea中心にするか、GitHub中心にするか。
3. 注釈の投稿条件・公開ライセンス・商用利用条件。
4. 初期のマージ責任者と、専門的判断を外部へ委ねる基準。
5. 一般読者の参加方法と、匿名・アカウント要件。
6. 本文・注釈のどこまでをオープン公開し、どこからを有料編集サービスとするか。
